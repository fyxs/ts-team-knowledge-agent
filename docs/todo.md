## 二、备份与容灾：方案未定（先记录已勘明的事实）

**范围界定**：本项目只负责**本机状态与治理数据**。原始素材（`D:\2Work\Knowledge\TS-Share`）的备份由用户侧负责，不纳入本项目。

已勘明的事实（2026-09-15 实测）：

```text
TS-Share 源文件                          94 文件 / 23.3 MB     只有 mos 一份（用户侧负责）
工作区非仓库部分（状态/日志/反馈/会话）   55 文件 / 约 1 MB      只有 mos 一份  ← 本项目范围
共享知识仓 knowledge-base                979 文件 / 36.8 MB    已在 GitHub ✓
应用代码                                                       已在 GitHub ✓
mos 已有备份脚本  win_backup.ps1 / backup_config.ps1 / backup_pack.py / run_daily_backup.bat
                  + .backup_key 均在
                  ⚠ 但没有挂任何备份计划任务（机制在，没在跑）
磁盘              C 盘剩 21.5 GB（紧）· D 盘剩 586 GB（宽裕）
```

威胁场景与对应手段：

| 场景 | 概率 | 靠什么防 |
| --- | --- | --- |
| 误删 / 误覆盖 | 最高 | 时间点快照（同盘无效，要异盘） |
| 整机故障 / 换机重装 | 中 | 异机副本 |
| 勒索 / DLP 异常加壳 | 低但致命 | 离线或远端副本 |
| 静默数据退化 | 中 | 非备份问题：靠巡检 + 幂等重扫（已具备） |

候选分层（数据量小，三层都做也不贵）：

```text
L1  同机异盘每日快照，保留 7~14 份
    防「误删」；C 盘空间紧张，落点建议 D 盘另一位置或外接盘
L2  加密打包推 GitHub 私有仓 Release
    复用 mos 现成脚本 + .backup_key，补挂计划任务即可
L3  离线 / 异机副本（移动硬盘，或 mos ⇄ mes 互备）
    防「勒索 + 账号层风险」，人工每月一次即可
```

需要用户定的三件事：

```text
1. 最怕哪种损失（误删 / 整机换机 / 勒索）→ 决定 L1/L2/L3 的先后
2. 是否有可用的移动硬盘或公司 NAS
3. 是否接受本机状态数据「加密后进 GitHub 私有仓」
```

**收口条件**：方案选定后必须完成一次真实恢复演练（解密 → 还原 → 起服务）；未演练不算完成。

## 三、服务鉴权（暂缓）

> 用户 2026-09-15 明确：暂不重要，先记在这里，后面视情况再定。

**现状（2026-09-15 实测）**

```text
监听      0.0.0.0:8088（不是 127.0.0.1），局域网可达
路由      16 个，全部无鉴权 —— 代码中既没有 Authorization 校验，也没有任何 auth 依赖
密钥      <工作目录>/secrets/model.key（服务端持有，可改用环境变量覆盖）
```

**两个后果**

```text
1. 会话库是本机的，而服务只有这一台 —— 能访问该端口的人可以看到本机完整会话历史
   （提了什么、答了什么、引用了哪些文档）
2. 模型额度共用 —— 任何能访问该端口的人都能消耗服务端配置的模型 Key
```

**候选方向（待定）**

```text
A. 保持现状      团队内网互信，接受会话可见与额度共用（最省事，但要有意识）
B. 只绑 127.0.0.1 最安全，但同事无法访问，与「拉到内网给同事用」的目标冲突
C. 加共享口令    一次输入、前端存本地，同事仍可用（折中）
```

**与已有决策的关系**：一期「不设管理员角色」是产品决策，不等于「不做任何访问控制」，两者需要分开判断。

**收口条件**：方向确定后需讲清「谁能访问、能看到什么、额度如何约束」，并在真实局域网设备上验证一次。
