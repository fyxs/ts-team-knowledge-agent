# TS Knowledge Agent：一期设计要点

> 本文承接最初的 V1 设计，已按**当前实现**校准。历史版本见 Git 记录。

## 1. 定位

面向小型团队的本地化 Agent 知识处理应用。成员按自己的习惯在本机提供和分类原始材料；应用负责发现、读取、转换、整理、沉淀和搜索。一期核心是**知识生产与问答**，不是执行型 Agent，也不是其他编码 Agent 的替代品。

## 2. 一期范围

```text
本地知识源目录
  → 文件扫描与变化识别
  → 按格式路由转换（MinerU / TXT 编码转换 / Markdown 直复制）
  → 质量门禁与凭据门禁
  → 写入共享 Git 仓的成员空间（Markdown + 必要图片 + 登记文件）
  → 本地全文索引
  → Web / CLI 检索与问答（带来源）
  → 可选：同步到共享 Git 仓
```

一期支持单公司场景，不配置公司范围与项目范围；项目、制度、模板等关系由源目录结构自然表达。

## 3. 固定约束

```text
知识仓固定为 git@github.com:fyxs/ts-team-knowledge-base.git
每个成员初始化时配置自己的成员标识（personal_workspace）
成员空间用于区分写入归属与维护责任；进入知识仓的内容默认团队共享，检索覆盖全部成员空间
原始文件所在位置就是原始源：只扫描、读取、转换、登记、搜索，
  不移动、不归档、不覆盖、不重命名、不删除
转换能力（MinerU）由应用在独立环境中管理，不要求成员手工安装
模型配置不写入知识仓；密钥存本机 secrets/model.key
本项目只存应用代码
```

## 4. 与初始设计的调整

| 初始设计 | 当前实现 |
| --- | --- |
| MarkItDown 作为转换器 | 已移除（效果不达标）。PDF / Office 用 MinerU；Markdown 直复制；TXT 编码转换 |
| 每轮有一层「提炼」环节 | 一期不做模型提炼，转换输出即知识结果 |
| AG-UI over SSE 作为事件协议 | 改为自建 SSE 事件协议；将来如需接第三方 UI 再在适配层引入 |
| 转换产物出现质量问题一律拦截 | **按来源区分**：源文件自身乱码 → 降级为 `quality_warned` 告警入库；转换工具引入的质量问题 → 拦截隔离 |
| Web 承载知识浏览 | 收窄为**轻量 Agent Web Chat**（问答 + 运行配置）；知识浏览交给 Obsidian / IDE |
| 会话数据随知识仓共享 | 会话与历史消息**只存本机**（`data/sessions.sqlite3`），属个人使用痕迹，不进共享知识仓 |

## 5. 输出结构

```text
<文档名>/
├─ <文档名>.md
└─ images/…

Excel：<文档名>/<文档名>.md + sheets/<工作表名>.md（大表按 5000 行分片）
登记：registries/<成员>/sources.jsonl、knowledge.jsonl、reviews.jsonl
```

不保留 `converted/`、`auto/`、`office/`、`candidate/`、`verified/` 等中间层，也不把 JSON、layout PDF 等中间产物写入知识库。

## 6. 质量与失败处理

```text
转换成功 ≠ 输出合格 ≠ 人工认可
质量门禁    空内容 / 乱码 / 无效 UTF-8 / 过短 / 缺标题
凭据门禁    命中凭据则隔离输出、标记 blocked_secret、阻断同步
失败语义    failed_retryable（可重试）/ quality_failed / blocked_secret
告警语义    quality_warned（源侧自身质量问题：入库可用但标记告警，不计失败、不占 error 语义）
            反馈记录区分 source_issue=true / adapter_issue=false
恢复        遗留 processing 超时回收为可重试；同工作目录单实例锁
```

## 7. 权限与安全边界

```text
能否推送到共享知识仓由本机 Git 凭据与仓库权限决定，Web 不另做权限体系
Web 默认只监听 127.0.0.1；对外开放时界面会成为本机 Git 凭据的代理，需确认网络范围
不记录文件正文、模型密钥、Token、密码；日志与数据库不入 Git
```
## 8. Web 交互约定

```text
定位        轻量 Agent Web Chat：问答 + 运行配置；不做知识库浏览器、文档管理、在线编辑；一期不设管理员
会话命名    首条提问自动成为标题，上限 20 字（服务端硬约束，前端限制只是体验）
会话列表    单行：会话名 + 更多菜单（时间标签不占行内空间，只用分组标题：今天 / 昨天 / 本周 / 更早）
重命名      行内编辑：Enter 提交、Esc 取消、清空后失焦回退原名；以服务端返回值落库
删除        确认框二次确认（本机数据，删除不可恢复）；删光最后一条后自动补建一个空会话
搜索        面板搜索为**按会话名过滤**；历史内容检索接口已就绪，页面入口待设计（见 docs/todo.md）
地址栏      ?session=<会话 id>，刷新与分享都回到同一会话；链接失效时回落最近一条并纠正地址栏
回答未检索  界面给出提示，说明该轮模型跳过了检索，引用区为空
```

## 9. 引用来源阅读

回答里的引用要让用户能自己判断「这条答案有没有依据」。分两层，各自解决一个问题。

```text
第一层 集中阅读   回答块上的「全屏」进入。整屏铺满，让出顶栏、会话列表和面板内边距换高度
                  （列宽 896 是阅读宽度，不该再宽；缺的是竖向空间）
第二层 来源阅读   引用行整行可点，叠在第一层之上，读被引用的那篇文档

都不放输入区   集中阅读的范围是「一条答案」，从这里提问会让「正在看哪条」变含糊；
              来源阅读是判断依据，不是继续对话。退出都只要一个 Esc，底部那 90px 还给正文
退出层级     两层去向不同，各退一层；Esc 不会一次退到底
入口唯一      引用行本身就是入口（行尾一个箭头），不再给第二个「全屏」按钮——一屏内同名主操作只允许一个
```

来源阅读头部与集中阅读同一套：文档名 + 右上角 ×；第二行是完整路径与总行数。
右端固定三件：命中处数、各命中行号按钮、×。**处数是值，行号按钮是去处。**

```text
落点      进层停在文档开头，不自动跳转到第 1 处命中
          落点是系统的、选择是用户的——一进来就落在第 1 处会被读成「已选中这一处」。
          命中片段在正文里已经标出，要跳哪一处由用户点行号按钮决定
行号按钮  进层一处都不预选（aria-current=false）；按钮标的是用户点过的去处，不是自动落点
文档加载  一次读全文，不做「继续读取下方」这类分页
          实测知识仓最大一篇 1344 行、整篇渲染 107ms——瓶颈出现之前不加机制
```

命中标记的规则：

```text
底色      灰底一档（--mark-bg，浅色 0.62 / 深色 0.50），文字仍是 --fg，对比只升不降
标题不参与 命中只落正文块（段落 / 列表 / 表格 / 引用 / 代码）
          标题短、检索词密度高，参与评分就会稳定挤掉正文行；点亮标题读起来像「标题被选中」，
          而它并不能说明答案出自哪一句话。ATX / setext / 整行加粗都算标题，代码围栏内不判标题
跨行内代码 SourceReader 逐文本节点各包一层 mark，产出 code 包 mark（不是 mark 包 code）；
          内层 mark 照常铺底——命中是一整句连续文本，高亮必须连续，中间破洞读起来像高亮断了
```

正文里的图片三种去向，取不到不等于看不见（不猜、不热链）：

```text
可显示    文档内相对路径重写为 /api/v1/knowledge/asset，实线边框 + 图片本身
站外地址  http(s) 图片给出可点入口，不自动加载（未随知识仓入库）
不可用    作者本机绝对路径（Typora 导出）取不到，虚线边框如实标出原因
```

数据层契约与实测缺口见 `citation-reader-data-contract.md`。

设计体系（配色、间距、圆角、动效与组件规范）以工程内 `design/` 为唯一来源，不在界面代码里硬编码数值。
